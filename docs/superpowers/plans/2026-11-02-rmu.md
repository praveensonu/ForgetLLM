# RMU integration

Implement RMU within the existing method registry, request schema, training
orchestrator and hyperparameter form. Reuse the forget-only and forget/retain
datasets and collators. Preserve the supplied example's answer-token activation
MSE, fixed random steering vector, and gamma/alpha weighting.

1. Add CPU tests for request validation, layer-derived regexes, LoRA placement,
   actual optimization in both data modes, frozen references and masked losses.
2. Add RMU configuration defaults and validation. Derive trainable parameter
   selection from layers on the backend and display the same derivation in the UI.
3. Adapt RMU utilities to the shared Trainer base, with separate trainer entry
   points for both data modes. Fail early on unmatched modules or parameters.
4. Wire the orchestrator and LoRA loader. Preserve existing adapter training;
   intersect RMU layer selection with parameters already marked trainable.
5. Add persistent frontend fields, payload mapping and validation; document use.
6. Run focused CPU training tests, repository tests, frontend build and browser
   interaction checks when available.

Implementation choices: default to the example's layers 22–28, steering 20;
derive the default activation module from the highest selected layer. Use one
selected GPU, as for existing reference-based trainers, to keep hooks and the
reference on the same device. Full-model mode updates selected layer parameters;
LoRA and existing-adapter modes update only their trainable adapter parameters.

Review focus: empty/invalid layers, stale parameter regex, missing module or
adapter layers, prompt/padding masking, reference frozen before any optimizer
step, and older projects restored without RMU fields.
